# Audit — 30 July 2026

State of the codebase at commit `e0f91a3`, before any Phase 0 work.

Line references point at that commit, so they will not match the current files. Each
finding carries its current status. Findings were verified by execution — brute-force
cross-checks of the geometry tables and targeted scripts against the running code — not
by reading alone.

**Verdict at the time.** The board geometry was genuinely good, which is the hard part of
Catan. What was missing was essentially all of the game: no rules engine, no economy, no
turn loop, and no state an AI could consume. `Game_2_players.py` was a scratchpad rather
than a game. Roughly **20% complete** against a trainable Catan.

## 1. What was verified correct

Every incidence map was cross-checked against independently derived ground truth:

| check | result |
|---|---|
| 54 vertices, degree histogram | 18 × deg-2 + 36 × deg-3 → 72 edges ✅ |
| tile → 6 vertices, all 19 tiles | all 54 vertices covered; 18/12/24 touching 1/2/3 tiles ✅ (114 = 19×6) |
| vertex ↔ vertex adjacency | fully symmetric ✅ |
| road → 2 endpoints | all 72 valid and distinct; set equals the 72 vertex-pairs exactly ✅ |
| vertex → roads | consistent with road → vertex ✅ |
| number token distribution | 18 tokens (one 2, two each 3–6/8–11, one 12) + desert ✅ standard |
| resource tile counts | 4 wood/wheat/sheep, 3 ore/brick, 1 desert ✅ over 200 boards |
| desert always on the "7" tile | ✅ invariant held |
| longest-road DFS | correct exhaustive search with correct backtracking ✅ |

The `find_longest_path` endpoint-inference trick — clustering a road's neighbours into two
mutually-adjacent groups, then identifying a vertex by the frozenset of roads incident to
it — produced canonical vertex ids and worked. It was later replaced because
`ROAD_VERTICES` states endpoints directly, making ~40 lines of inference unnecessary.

## 2. Confirmed bugs

### B1 — Two wrong entries in the road-adjacency map 🔴 → ✅ fixed

`Board.py:324` and `Board.py:373`; the only 2 errors in 72 entries, both asymmetric.

```
road 2  = (1, 5),   road 3  = (2, 5)  share vertex 5,  but 3 ∉ neighbours(2)
road 51 = (35, 40), road 43 = (30, 35) share vertex 35, but 43 ∉ neighbours(51)
```

Longest-road undercounted and legal-road enumeration silently omitted moves whenever a
player's network touched vertex 5 or 35. Worse, `get_adjacent_roads_from_road` was also
what `find_longest_path` used to *infer* vertex identity, so a bad entry corrupted the
vertex itself.

*Resolved by generating the relation from coordinates — see
[decision 0001](decisions/0001-generate-geometry-from-the-row-structure.md). Pinned by
`test_regression_roads_2_and_51_have_their_missing_neighbour`.*

### B2 — Nothing ever costs resources 🔴 → ⬜ Phase 1

`place_road` / `place_settlement` never touched `player_ressources`. Verified: a player
holding exactly 1 brick + 1 wood built **every remaining road**; the only binding
constraint was the 15-piece limit. `check_player_actions()` reported affordability and was
never used to spend.

### B3 — No connectivity rule outside the setup phase 🔴 → ⬜ Phase 1

Verified: `place_road(1, 70)` succeeded on an empty board with no adjacent road or
settlement. `check_valid_road_once_game_has_begun` /
`check_valid_settlement_once_game_has_begun` computed the legal sets, but `place_*` never
consulted them.

### B4 — Setup phase silently ate a road 🔴 → ✅ fixed

`Game_2_players.py:129-137` and `:162-170`. `available_roads` came from
`get_adjacent_roads_from_settlement` **unfiltered** by occupancy, so it listed roads that
were already built. Picking one made `place_road` return an error — and the loop `break`ed
anyway. The player kept the settlement and lost the road.

*Both halves fixed: the getter filters, and the loop repeats until placement succeeds.
Pinned by `test_setup_phase_never_costs_a_player_their_road`.*

### B5 — The board could not say who owns what 🔴 → ⬜ Phase 1

`delete_settlement_position` removed the vertex **and its neighbours** from a single
"available" list. Three distinct states — **empty**, **blocked by the distance rule**,
**occupied by player N (settlement vs city)** — collapsed into one bit.

The single biggest structural blocker. Road-blocking, city upgrades, robber stealing and
every AI observation depend on separating them. Still open; owned by Phase 1's
`GameState`.

### B6 — Shared mutable class attributes 🟠 → ✅ fixed

`Game_2_players.py:8-9`. Verified: `g1.player_order is g2.player_order → True`.
`random.shuffle` mutated the **class** list in place, so every game instance in the
process shared turn order. Fatal for self-play and parallel rollouts. The same
anti-pattern was in `Dice.py:4` and all of `Deck.py`.

### B7 — Import executed a game 🟠 → ✅ fixed

`Game_2_players.py:437` — a module-level `game = Game_2_players()`. Verified: importing
the module emitted 2,395 characters of stdout and played a game. No `__main__` guard.
`Board.__init__` also called `display_board()` and printed the whole intersection dict.

### B8 — Longest road: two real gaps 🟠 → ⬜ Phase 2

- **No break at an opponent settlement**, which is the official rule. Nothing looked at
  other players.
- **Intersection reuse.** For `{7,11,12,19,20,25,26,27}` the code returned **7**; the
  strict simple-path answer is **6**. The extra segment came from passing through vertex 8
  three times, using all three of its roads.

Current behaviour is pinned by a test so it cannot change silently, but the ruling is an
open decision — [0006](decisions/0006-longest-road-intersection-reuse.md).

### B9 — Variable shadowing 🟠 → ✅ fixed

`Game_2_players.py:97`: the inner `for road_position in adjacent_roads` shadowed the outer
loop variable. It happened to work because the outer `for` reassigned each iteration.

### B10 — Type-inconsistent returns 🟡 → ✅ fixed

`Board.py:255`, `:317`, `:397`, `:477` returned the **string**
`"The number must be between 1 and 54."` for out-of-range input instead of raising.
Callers iterated the result — `for adjacent in adjacent_positions` would have looped over
its characters. Now `check_id` raises `ValueError` / `TypeError`.

### B11 — Wrong bank size 🟡 → ✅ fixed

`Deck.py:2-6` had 21 cards per resource. Standard Catan is 19. (Dev card counts were
already correct: 14/5/2/2/2 = 25.)

### B12 — Getter aliasing 🟡 → ✅ fixed

`get_available_settlements()` returned the internal list object, so callers could mutate
board state. Getters now return sorted copies.

### B13 — README inaccurate 🟡 → ✅ fixed

Claimed `pip install -r requirements.txt` (no such file), online multiplayer, and city
upgrades — none of which existed. Zero tests, no package structure.

## 4. Blockers specific to AI-interpretability

The stated goal is training an agent, and the architecture could not be trained against.

**4.1 — No state object.** State was scattered across `Board.settlement_positions` (a
shrinking list) and `Player.player_road_position` (sets), mutated destructively. Nothing
could serialize, clone or diff a game. MCTS and self-play both need cheap `clone()`.
*Phase 1.*

**4.2 — No action space.** No enumeration of legal moves as a fixed-size discrete set, and
no legal-action mask. This is *the* prerequisite for RL. *Phase 3.*

**4.3 — Observations unencodable.** `positions_grid` was
`{vertex: [{number: resource}, …]}` — a list of single-key dicts that also discarded which
*tile* each entry came from, which the robber needs. *Replaced in Phase 0 by
`vertex_production: vertex → tuple[Production(tile, number, resource)]`, plus a
payout index keyed by roll.*

**4.4 — Performance ~1000× off.** Every adjacency lookup **reconstructed a 54- or 72-entry
dict literal from source**: measured **5.49 µs/call**. `find_longest_path` called it inside
a nested loop, so one longest-road evaluation cost thousands of dict constructions. RL
needs 10⁵–10⁶ steps. *Fixed in Phase 0 — 38 ns/call.*

**4.5 — I/O fused into the logic.** `input()` in the placement flow, `print()` in
`Board.__init__` and every game method. No training loop can call that. And no seeding:
`random` was used globally, so no reproducible episodes or eval sets. *Fixed in Phase 0.*

Same board layouts and same longest-road answers, verified against the original code from
